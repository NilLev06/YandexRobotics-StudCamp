# Visual-Inertial Odometry — статус и путь к нему

Полноценный VIO сейчас **невозможен**: три блокера подряд. Этот файл — честный
статус, что уже починено, что осталось, и что делать дальше. Пока нет
подтверждённой калибровки — не подключать ни к чему безопасность-критичному
(EKF/Nav2), только диагностика/логирование, как слой "замечено камерой" на
карте.

## Блокеры

1. **✅ Почищено.** ROS-нода камеры (`camera_ros`, публикует настоящие
   `sensor_msgs/Image`+`CameraInfo`) существует в `packages/main/launch/camera.yaml`,
   но не была включена в `main.yaml` — из камеры реально запускался только
   RTSP-проброс для YOLO. Осталась опциональной специально: сенсор камеры на
   этом железе, скорее всего, **однопоточный** (libcamera обычно не даёт двум
   процессам открыть один сенсор одновременно) — включение в постоянный
   автозапуск рискует сломать уже работающий YOLO-стрим. Запускать вручную:
   ```sh
   ros2 launch main camera.yaml
   ```
   но **только когда `docker-compose.yolo-live.yaml` остановлен**, либо после
   проверки на реальном железе, что оба потребителя камеры могут работать
   одновременно (не проверено, требует теста на месте).

2. **✅ Почищено.** `camera.yaml` ссылался на `camera_info.yaml`
   (калибровка камеры), которого в репозитории физически не было — нода бы
   тихо не подгрузила калибровку. Убрал битую ссылку: теперь `camera_ros` без
   `camera_info_url` честно публикует **неоткалиброванный** `CameraInfo`
   (нулевая матрица, `D=[]`) вместо того, чтобы выдавать себя за
   калиброванный. Добавить `camera_info_url` стоит только после реальной
   калибровки шахматной доской (`ros2 run camera_calibration
   cameracalibrator`).

3. **❌ Не проверено.** Установленный `ros-jazzy-rtabmap-odom` заточен под
   RGB-D/стерео (нужна карта глубины). У нас одна обычная RGB-камера без
   глубины — неизвестно, согласится ли его `rgbd_odometry`-нода работать в
   режиме "только RGB, без глубины" (монокулярная одометрия с неизвестным
   масштабом) без дополнительной настройки. Требует проверки на реальном
   роверe — команда для первого теста (после блокера 1):
   ```sh
   ros2 launch main camera.yaml &
   ros2 run rtabmap_odom rgbd_odometry --ros-args \
     -r image:=/camera_node/image_raw \
     -r camera_info:=/camera_node/camera_info \
     -p subscribe_depth:=false \
     -p publish_tf:=false \
     -r odom:=/vio/odom
   ```
   `publish_tf:=false` обязателен — иначе нода начнёт публиковать `tf`,
   конфликтуя с уже работающим деревом трансформаций от EKF/ICP.

## Что дальше, по порядку

1. Проверить блокер 3 на реальном роверe (команда выше)
2. Если запустилось и даёт разумные (пусть и в непонятном масштабе) числа —
   подключить как **диагностический** топик `/vio/odom`, показать в
   дашборде/карте рядом с остальными "неточными" слоями (по аналогии со
   слоем "замечено камерой") — никогда не фьюзить в EKF без отдельного
   разговора и калибровки
3. Откалибровать камеру (интринсики) — нужно и для VIO с реальным масштабом,
   и для approach-режима поиска объектов (`search_calibration.json`) —
   это общая работа, одна калибровка закрывает оба случая
4. Только после калибровки и достаточного количества успешных тестов —
   обсуждать, стоит ли вообще фьюзить VIO в навигацию (может не понадобиться,
   если лидарной одометрии достаточно)
