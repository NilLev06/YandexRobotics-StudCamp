# Карта ровера

Отдельный модуль, не зависит от `TELEMETRY.md`/дашборда. Только читает
ROS-топики, никогда не командует движением.

## Из чего физически можно строить карту

На роверe нет радара — есть лидар, камера, IMU и одометрия. Честная оценка
того, что каждый датчик даёт для карты:

| Слой | Источник | Точность | Когда доступен |
|---|---|---|---|
| **Occupancy (препятствия)** | лидар → SLAM `/map` | сантиметры | всегда, пока работает SLAM |
| **Облако точек (лидар)** | сырые точки `/scan`, накапливаются в кадре `map` | сантиметры — тот же сенсор, что у occupancy, просто плотнее и без растеризации в клетки | всегда, пока приходит `/scan` и есть TF `map`→кадр лидара |
| **След ровера** | одометрия/`tf` | сантиметры | всегда |
| **Подтверждённые объекты** | лидар + камера вместе | сантиметры | только в approach-режиме (`calibrated: true`) — там, где лидар физически ассоциируется с боксом YOLO |
| **Замеченные камерой** | только камера | **нет измеренной дистанции**; рисуется как луч-направление, с приблизительной длиной (см. ниже) | во время активного поиска, без полной калибровки |
| **Обзор камеры** | допущение "смотрит вперёд" | не измерено — угол крепления камеры относительно `base_link` физически не откалиброван | всегда, пока известна поза ровера |

**Приблизительная дистанция для "замеченных" объектов.** Раз камера видит объект без лидара, точного расстояния нет — но можно грубо прикинуть по известному фокусному расстоянию камеры (`camera.intrinsics.fy_px` в `config/search_calibration.json`) и типичному реальному размеру объекта его класса (маленькая таблица в `object_search.py`: bottle ≈ 25 см, chair ≈ 85 см и т.д.). Это не измерение — не учитывает наклон, ракурс, нетипичный размер конкретного экземпляра — и никогда не используется для навигации, только для подписи на луче в UI. Пока `fy_px` не измерен (сейчас `null`), просто не считается и не показывается.

Что сознательно **не** сделано и почему:
- **Тепловая карта Wi-Fi** — данные для неё уже есть (телеметрия пишет
  `wifi_dbm`), но чтобы отрисовать её здесь live, этому сервису
  понадобился бы доступ к Wi-Fi хоста — то есть привилегия, которую мы
  принципиально не даём ни одному сайдкару в проекте. Если понадобится —
  делать отдельно и осознанно, не молча.
- **Карта по батарее/температуре** — это не пространственные данные
  (значение не зависит от места), как карта бессмысленна; уже есть в виде
  графика в `docker-compose.dashboard.yaml`.

## Несколько карт как пресеты

Вместо отдельных страниц под каждый тип карты — один набор чекбоксов-слоёв
плюс кнопки-пресеты в шапке ("Всё", "Только карта", "Только облако точек",
"Только след", "Только объекты"), которые просто переключают эти же чекбоксы. Логика та же: слои
строятся независимо, комбинируются в момент отрисовки — пресеты лишь готовые
комбинации, без дублирования кода/страниц.

## Файлы

```
mapping/
├── map_view.py                  # ROS2-нода + HTTP-сервер, все 4 слоя
├── docker-compose.map-view.yaml # запуск как непривилегированный сайдкар
└── README.md                    # этот файл
```

`map_view.py` рисует базовую occupancy-карту как JPEG (`/map.jpg`), а
остальные три слоя отдаёт как векторный JSON (`/api/layers`) — след,
найденные объекты, замеченные объекты. Браузер сам рисует их поверх карты
на `<canvas>` и включает/выключает чекбоксами в шапке. Это и есть "строим
по отдельности, потом объединяем": каждый слой — независимый источник
данных, комбинируются только в момент отрисовки в браузере.

## Запуск

Требует уже работающего SLAM (`/map` публикуется основным контейнером `ros`
как часть обычного bringup).

```sh
cd ~/z_boys/mapping
docker compose -f docker-compose.map-view.yaml up -d
```

Открыть: `http://<ip-ровера>:8093/`, либо кнопка "Карта" в шапке центра
управления (`../docker-compose.portal.yaml`).

## Топики

- Подписки: `/map` (`nav_msgs/OccupancyGrid`), `/scan` (`sensor_msgs/LaserScan`),
  `/tf`, `/search/found`, `/search/sighted`, `/search/photo`
- Ничего не публикует и не вызывает сервисы/actions — read-only нода

`/search/found` и `/search/sighted` публикует `scripts/object_search.py`:
`found` — только при успешной лидар-ассоциации (approach-режим), `sighted`
— на каждый новый трек детекции камеры, независимо от калибровки (это и
есть "замечено камерой", без точной дистанции).

## Фото на карте

Карта строится из лидара (единственный сантиметрово-точный источник
геометрии) — но раз камера физически стоит на роботе, реальные кадры с неё
можно приколоть к точкам на этой же карте, а не только рисовать абстрактный
луч/точку. При каждом новом `found`/`sighted`-событии `object_search.py`
тянет текущий кадр с `yolo-live` (`/snapshot.jpg`) и публикует его как
`sensor_msgs/CompressedImage` на `/search/photo`, с общим `photo_id` в
заголовке сообщения — тем же id, что лежит в JSON `found`/`sighted`.
`map_view.py` держит эти кадры в ограниченном FIFO-кэше в памяти (последние
`MAX_PHOTOS = 80`, не привязано к времени жизни самих маркеров) и отдаёт по
`GET /photo/<id>.jpg`. На карте точки с фото — с тонким кольцом (`found`)
или маленькой точкой на конце луча (`sighted`); клик по ним открывает
фото поверх карты.

Это не реконструкция пространства — сама геометрия карты по-прежнему только
из лидара, камера лишь подписывает точки реальными кадрами. Публикация фото
— best-effort и никогда не мешает поиску: сбой загрузки снапшота просто
оставляет `photo_id: null` в сообщении, и точка на карте рисуется как
раньше, без кольца/точки и без клика.
